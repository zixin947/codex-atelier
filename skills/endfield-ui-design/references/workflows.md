# 工作流与交付

## 研究

先确定载体与具体画面，再查看官方/用户截图，补充社区实现。把事实与建议分开，记录 URL、日期、版本/平台、视口和核验程度。只给出找到的内容，不声称“全网全量”。

产物可包括来源索引、截图、测量 JSON、观察笔记和待补清单。研究本身不授权修改应用、安装库、读凭据或提取游戏资源。

## 设计

从用户目标选一个家族与一个主视觉关系。先排灰阶层级，再加信号色、形状与少量纹理，最后决定状态与动态。已有要求够明确就直接做，不强制用户反复批准。

若信息不足会改变结果，问最关键的一点；其余能独立完成的部分继续。方案文字应帮助判断，不替代真正可审阅的画面。

可用 [任务模板](../assets/design-brief.md)，但小改动不需要填整份模板。

## 实现

检查现有组件和主题机制，使用统一令牌。先完成一个关键页面/控件，再扩展同系统；完成默认、悬停、按下、选中、禁用、加载、空与错等相关状态。

用当前项目能实际运行的命令验证，查看真实渲染，实际操作关键交互。截图发现问题后修正；不为了交付截图掩盖真实功能。

外观修改通常不需要新增后端测试。只有业务逻辑、数据映射或服务边界变更时才补相应验证，避免测试与实现同义反复。

## 审查

遵守只审不改。按可用性/数据真实性、可访问性、布局、视觉一致性、动效与性能排序。每个问题写明位置、触发、可见后果与证据；美术偏好和功能缺陷分开。

可以使用 [审查模板](../assets/review-report.md)。不要凭文件名推断运行效果，也不要声称静态代码审查等于原生验收。

## 交付格式

根据任务简洁说明：完成了什么、可查看的文件/画面、实际验证、仍待验证。来源与版权条件放到相关文件，不用重复长免责声明。

用户只要求提交推送时，检查范围与 diff、执行必要检查并推送；不要重跑整套 UI 开发流程。未请求发布时不自动推送或创建 PR。

## 维护证据

官网/仓库变化时更新对应记录，不覆写旧证据成为新日期。截图重命名或删除时同步更新清单和哈希。新的“官方”规则先补原始证据，再进入规范；无法独立复核的社区判断继续标为社区。
